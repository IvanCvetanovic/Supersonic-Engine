# Execution plan — all six workstreams

Ordering is dictated by the report's own gates, not preference:
- **F is explicitly gated on C** ("do C first — every item here is currently unmeasured").
- **E is strictly internally ordered** (SAT/OBB manifolds → speculative contacts/CCD → warm-started
  solver + sleeping → delete the ground plane). CCD's conservative advancement routes through
  `PhysicsSystem::Raycast`, which is AABB-based, so it *must* land after the OBB work.
- **A's `AssetRoot()`/`ResolveAssetPath()` chokepoint subsumes** the packaged-game path defect, so
  that correctness item is folded into A rather than fixed twice.
- **D's transparent pipeline wants the depth `storeOp` flip**, which also unblocks SSAO/fog later.
- **B's ABI widening wants the `static_assert` layout pin first**, so a struct change cannot ship
  silently while the pin is being added.

Every phase ends green: `cmake --build build --config Debug` + `ctest --test-dir build -C Debug`.
One commit per coherent change, matching the repo's existing message voice.

## Phase 7 — F, scale  **MOSTLY DONE** (8c723aa, e8ad9d3, 25e2fa6, fa6cfa5, 5e5976d)

Also done: build-config honesty in the profiler, SyncResources signature gate,

The remaining F items were SCOPED by review and three of them should not be
done as written:
- batched fenced UploadContext -> do-later. Zero against the frame; no upload
  runs in a steady frame. It buys startup only (~28 queue drains on frame 1).
- per-frame render targets -> DO NOT. Close to zero value and structurally
  antagonistic to the shadow cache, whose premise is that shadow content
  persists between frames.
- opaque draw sorting -> do-later. Bounded at 0.2-0.5 ms of a 34 ms debug
  frame, and possibly exactly zero depending on scene authoring.
- clustered forward -> still last, still the big one.

KEY FINDING: all Phase 7 measurements were debug-build until late. Release is
2.6x to 210x faster per zone and REORDERS the frame. Only the shadow cache and
the hierarchy index are large wins in release.
NEW, from measurement at 500 entities: Editor UI is 8.8 ms and dominates
everything - the Scene Hierarchy panel lists every entity every frame; and
Resource Sync is 2.6 ms walking every entity every frame. Neither is on the
original F list.
One flat `ShadowCaster` array built once and tested in all 18 passes; `Frustum::FromMatrix`

`VulkanRenderer.cpp:836-841` documents why). Batched fenced `UploadContext` replacing the three

Clustered forward last: directional lights stay in a small always-on list outside the froxel grid,
so `shader.frag:377`'s `i == 0` gating survives clustering.

# Phases 8-14 — derived from two real games, not from the audit

Added 2026-08-19 after reading **Wolf Brigade** (Godot 4.7, 2D lane RTS, Android-primary) and
**HUSK** (Rust/Bevy, 3D deterministic RTS) and asking whether this engine could host them.
Answer: Wolf Brigade no, HUSK partly - the simulation yes, the game no.

**These run AFTER Phases 3-7, by the owner's decision.** Recording the ordering tension rather
than silently acting on it: neither game would use A's drag-and-drop asset assignment (Wolf
Brigade authors nothing in an editor, HUSK builds worlds from `.map.ron`), and two items in B are
actively harmful to HUSK - `addForce` and velocity on entities a deterministic sim owns is exactly
the coupling that desyncs a fixed tick. A's *runtime* half (SceneManager, AssetRoot,
Invalidate/Release) is validated by both games; its editor half is validated by neither.

None of the engine's famous limitations block either game. Not the 8-light cap, not
box-box-as-AABB, not the missing CCD, not the missing navmesh. HUSK's TECH_NOTES.md says a physics
engine "would fight determinism"; Wolf Brigade contains no collider anywhere. Phase 6 (E) buys
these two games nothing except its final item - deleting the unconditional ground plane.

## Phase 8 — The application seam (the one true blocker for both)
`entt::registry m_registry` is private (SupersonicApp.hpp:67, `private:` at :37) and the frame body
is a fixed sequence with no callback and no system-registration point. HUSK's 22-system chained
schedule and Wolf Brigade's nine singletons have nowhere to live except inside SupersonicApp.cpp.
- A layer/system interface with per-frame callbacks, and access to the registry.
- Paired with the *subtraction* the plan already knows about: split the ImGui backend out of
  `VulkanRenderer` (which includes `editor/Theme.hpp` today) and stop the scene pipeline pointing
  at the editor's offscreen render pass (SupersonicApp.cpp:126-127). The plan framed that as
  getting the editor OUT; both games need getting a game IN. Same coupling, opposite direction.
- The editor grid draws unconditionally at the end of the scene pass
  (VulkanRenderer.cpp:978-983) with no game-mode check. Visible artifact in any shipped game.

## Phase 9 — A fixed-tick game clock, sim/render split, interpolation
The only fixed step is physics-internal, and it CLAMPS the frame delta to 100 ms before
accumulating (SupersonicApp.cpp:504) and zeroes the remainder after five steps (:561-562).
- A game tick separate from the physics step, at an authored rate.
- `prev`/`cur` transforms and interpolation by overstep fraction, or a 20 Hz sim visibly stutters.
- Determinism discipline: the engine currently violates its own would-be rules - `ScriptEngine.cpp:246`
  accumulates `elapsed` from variable frame deltas and drives `std::sin` off it (:256-257).
  A tick counter, a state hash oracle, and a CI gate on reproducibility.
- **Do not copy the existing fixed step for this.** Discarding simulated time under load would not
  break bit-exactness, but every mission timer and production queue would run in slow motion.

## Phase 10 — GPU resource lifetime
`MeshRegistry` and `TextureRegistry` are write-once: no update, no free, no eviction, storage and
lookup private (MeshRegistry.hpp:29-58, TextureRegistry.hpp:25-60). A key hit returns the cached
id. HUSK rewrites a 240x240 fog texture every frame - same key is a no-op, fresh key leaks a
`VkImage` per frame - and every mission transition leaks its terrain mesh and minimap image.
- `Release` and `Replace` on both registries.
- GPU lifetime tracking across frames in flight, so a freed image is not still referenced by a
  submitted command buffer. The fiddly item, and the one with the most downstream value.
- Overlaps A's AssetDatabase `Invalidate`/`Release`; do them together if A has not shipped yet.

## Phase 11 — A blended pass, emissive, and fog
`blendEnable = true` appears exactly ONCE in the renderer, for the editor grid
(VulkanRenderer.cpp:301). `shader.frag` computes an alpha the blend state discards.
- Transparent bucket, back-to-front sort, per-material opaque/transparent split. This is Phase 5's
  transparency item, reclassified: it is not a quality item, it is **fog of war**, the
  build-placement ghost and the construction state - mechanics that do not exist without it.
- **Emissive**: `EMISSIVE` names a material on 29 of HUSK's 58 models and is its entire team-state
  visual language, driven above 1.0 to trip bloom. Nothing in `src/` or `assets/shaders/` mentions
  it. Everything downstream already exists and `PushConstantData` has 24 spare bytes of its
  guaranteed 128 (VulkanPipeline.hpp:75-86). One vec4 and one add. Cheapest high-value item here.
- Distance fog, and bloom threshold/knee/intensity/exposure as runtime values rather than
  compile-time constants (BloomPass.hpp:50-53).

## Phase 12 — Draw scale
One `pushConstants` + one `drawIndexed` per visible entity, no instancing, no material sort
(RenderSystem.cpp:184-229), re-run per shadow cascade.
- Instancing keyed by mesh+material. Does **not** fit a push-constant-per-draw layout without
  changing the layout - that is the actual work, not the instanced draw call.
- Opaque sort by material, so the existing rebind-avoidance stops being inert.

## Phase 13 — A serializer a game can extend
`ComponentCodec` names 18 engine components and cannot be opened to a game's own types. Wolf
Brigade's mid-match save and HUSK's `SAVE_VERSION 6` snapshot are made of components it will never
name. Also: `PrefabSerializer::InstantiatePrefab` re-opens and re-parses the file on every call
with no cache (PrefabSerializer.cpp:49-89) - unusable at RTS spawn rates.

## Phase 14 — What Wolf Brigade needs, and probably is not worth it
Listed for completeness and honestly labelled. This is a mismatch of kind, not a feature gap: a
flat unlit 2D presentation model is effectively a second renderer, and Android is a windowing
rewrite. Recommend NOT doing this unless the 2D target becomes a goal in its own right.
- Orthographic camera: `getProjectionMatrix` hardcodes `glm::perspective` (Components.hpp:172-176);
  the only `glm::ortho` in the tree is the shadow projection (ShadowCascades.cpp:198).
- An unlit shading path. One scene pipeline, full Cook-Torrance, hemisphere ambient that tints top
  and bottom differently - visible immediately on flat quads. `MaterialComponent` has no
  shading-model field and there is no pipeline variant system.
- World-space text. `UITextComponent` is screen-anchored by construction (Components.hpp:465-467).
- UI: layout containers (the model is nine anchors plus a pixel offset), z-order that is currently
  fixed by system - all panels, then all buttons, then all text (UISystem.cpp:46/75/112), so a
  modal overlay has every button showing through it - and `UIInput::Update`'s "did the UI take this
  click" result, which is called as a bare statement and discarded (UISystem.cpp:42).
- Per-entity colour and visibility reachable from game code.
- Android: native activity, surface loss/recreate, lifecycle, touch through `RawInputState`
  (Input.hpp:74-83 has keys/mouse/pad and no touch concept), and compressed textures - uploads are
  uncompressed RGBA8 today (TextureRegistry.cpp:110-190).
