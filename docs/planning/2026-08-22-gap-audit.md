**Short answer: yes, but not where the roadmap says.** The engine and editor are substantially built — what is missing is the *game* seam: nothing a shipped game can execute can switch scene, rebind a key, pick a quality level, or author behaviour without recompiling the engine itself. Compounding that, the docs are stale in the shipped direction — four and a half of the six README Roadmap "Next" bullets describe work that already landed — so the roadmap currently misdirects anyone (including you) deciding what to build next.

## 2. PROMISED BUT UNSHIPPED

- **Image-based lighting** — `README.md:311`. The whole environment is `hemisphere(N)` at `shader.frag:397` and `hemisphere(R)` at `:414`, a two-colour mix defined at `:158`. The split-sum machinery is there (`EnvBRDFApprox` `:170-179`) with no image-based source; `TextureRegistry.cpp:125` creates every image `arrayLayers=1, cubeCompatible=false` from 8-bit `stbi_load`, so an HDRI cannot be authored at all. *Effort: a week-plus — cubemap loading, an offline irradiance/prefilter bake, a BRDF LUT and two new descriptor bindings. This is the largest single promise outstanding, and it unblocks metal and smooth dielectrics reading as anything other than plastic.*
- **Light culling** — `README.md:314`. `gatherLights` at `VulkanRenderer.cpp:594` opens with `if (count >= kMaxLights) break;` over `registry.view<LightComponent>()` — no distance, intensity or screen weighting anywhere in `:559-684`, no log when the cap is hit. - **A game-facing way to switch scene** — `README.md:308`. `SceneManager` is a private member of the editor (`EditorLayer.hpp:190`), every caller is `EditorLayer.cpp:361/364/479/582`, `EngineLayer` is handed only `entt::registry&` (`EngineLayer.hpp:45/60/72`), and the ABI's world block (`ScriptPluginApi.h:161-175`) has no scene function. A layer *can* call `SceneSerializer::Deserialize` (`SceneSerializer.hpp:20`) today — but doing it from `OnUpdate` is precisely the mid-iteration hazard `SceneManager.hpp:20-25` was written to defer around. So what is missing is a *supported* seam, not the capability. *Effort: a day — move SceneManager into the registry context and add one ABI entry. Unblocks menu→level, level→level and restart-on-death; today a packaged game is exactly one scene.*
- **The glTF material story** — `README.md:59` and `ARCHITECTURE.md:130` both claim materials and texture references. - **Asset identity that survives a rename** — the bullet at `README.md:306` is literally headed "Asset identity:", and there is none. ## 3. PARTIAL — shipped, but the incompleteness bites

**Fix today (small, and each one is a correctness bug or a data-loss path)**

- **The sky erases every transparent surface against it.** `RenderSystem::Render` runs both the opaque and transparent passes (`VulkanRenderer.cpp:1149`) and the sky triangle is drawn *after*, at `:1156`. The transparent pipeline has depthWrite off (`:319`), so under a blended pane depth still holds the clear value 1.0 (`:1130`); `sky.vert:29` emits z=1.0, compare is eLessOrEqual (`VulkanPipeline.cpp:120`), and `skyOptions` (`VulkanRenderer.cpp:336-340`) never sets blendEnable so it defaults false (`VulkanPipeline.cpp:138`). Glass in an exterior wall, water at the horizon, any fade against sky — erased. It looks like transparency working indoors and vanishing outdoors. *Effort: move one draw call. Unblocks exterior transparency entirely.*
- **Particles are drawn on the opaque pipeline.** `RenderSystem.cpp:447` explicitly rebinds it ("the particle block below assumes it is bound") and pushes `particle.color` with alpha at `:484` into a pipeline with blendEnable false. `ParticleEmitterComponent::endColor` defaults to alpha 0 (`Components.hpp:647`), so every emitter is authored to fade and none does. Sharpest detail: `Components.hpp:302-310` names particle alpha as one of the motivations for the transparency work — the fix landed for materials and skipped the case its own comment cited. *Effort: an hour or two.*
- **The dirty flag is never set.** `SceneManager::MarkDirty` (`SceneManager.hpp:36`) has callers only in `tests/test_scenemanager.cpp:103/112/129/152`, and nothing anywhere reads `IsDirty()`. New Scene (`EditorLayer.cpp:363`), Ctrl+O (`:358`), a double-clicked tile (`ContentBrowserPanel.cpp:224`) and Exit (`:373`) all wipe the registry with no prompt and no title-bar marker. *Effort: a day. Unblocks not losing a session to a stray double-click.*
- **Save as Prefab silently overwrites.** The path is `"assets/prefabs/" + sanitised tag + ".prefab"` (`EditorLayer.cpp:575`) and `PrefabSerializer.cpp:30` opens `std::ofstream file(filepath)` with no `exists()` check, then returns `{ true, "Saved prefab to ..." }`. Default tags collide immediately — every hierarchy "Create Cube" names itself Cube.
- **Shared-material edits bypass undo and are lost on exit.** `InspectorPanel.cpp:318-346` mutates `MaterialLibrary` state directly while `EditHistory::capture()` (`EditHistory.cpp:9`) snapshots only `SceneSerializer::SerializeToString`, which never sees the library. The only `MaterialLibrary::Save` in the tree is the manual button at `InspectorPanel.cpp:346`. The one workflow the README sells as "one asset, many entities, edited once" is the one with no undo and no save-on-exit.

**Rendering**

- Fog stops at the horizon: `shader.frag:453-459` fogs geometry, `sky.frag` contains zero occurrences of "fog" and `:58` writes `vec4(sky, 1.0)`. Defaults make it maximal — `RenderSettings.hpp:46` fog is `{0.55,0.60,0.68}`, ambient defaults are near-black (`Components.hpp:267-268`). Turning fog on makes the scene look more broken.
- Transparent surfaces cast solid black shadows: `GatherShadowCasters` (`RenderSystem.cpp:152`) filters on visibility and `castsShadow` only, never consults `MaterialComponent::transparent` (`Components.hpp:320`), and `shadow.frag` has no alpha test.
- Emissive and transparency cannot live in a `.material`: `MaterialAsset` (`MaterialLibrary.hpp:18-26`) holds six fields, and Sync/MakeUnique/Assign (`MaterialSystem.cpp:33-38/:50-56/:72-78`) copy exactly those. A linked entity *keeps* its emissive and transparency — but the inspector widgets sit in the else-branch that only runs when unlinked (`InspectorPanel.cpp:311-353`), so once linked the values become un-editable, unshareable and unversioned.
- Only two point and two spot lights can cast shadows, first-come-first-served: `VulkanRenderer.cpp:617` and `:633` against `kMaxShadowCasters = 2` (`PointShadow.hpp:32`, `SpotLight.hpp:25`), while `README.md:292` ticks "point and spot shadows" with no caveat. The inspector does disclose the policy (`InspectorPanel.cpp:649-658`) — what it cannot tell you is *which* two won, or let you prioritise.
- Uploads drain the graphics queue: `VulkanImage.cpp:237/:356/:404` and `VulkanBuffer.cpp:124` each end in `waitIdle()`, and `QueueFamilyIndices` (`VulkanDevice.hpp:17-24`) has no transfer family to move them to. (Not mid-recording — `RenderSystem.cpp:81-82` and `SupersonicApp.cpp:936` deliberately upload first — but a full drain on the frame that loads an asset, with no background path.) `JobSystem` exists and neither registry uses it.
- Submission is one draw per entity in registry order: `RenderSystem.cpp:336` iterates unsorted, the only rebind avoidance is the neighbour-match checks at `:368/:380`, every draw is `instanceCount 1` (`:393/:442/:493`), and `multiDrawIndirect` "stays off until something needs" it (`VulkanDevice.cpp:221`). A 500-particle emitter is 500 draws with a push-constant each (`:493`).
- No GPU timing: `Profiler.hpp:12-14` names "no CPU zones, no GPU queries" as the problem it solves and only the CPU half landed — sixteen wall-clock zones at `:21-51`, zero `vk::QueryPool` anywhere in `src/`. You cannot tell whether a scene is GPU-bound.
- Quality is compile-time: `VulkanOffscreen.cpp:15` hardcodes 4× MSAA, `VulkanSwapchain.cpp:63-71` always prefers Mailbox with no vsync request, shadow resolution is a constructor default (`VulkanRenderer.cpp:35-37`), and `LaunchOptions.hpp:14-53` carries no resolution, vsync or quality field. A packaged title ships with all of it locked on and no API to build an options menu from.

**Physics**

- Speculative contacts are never reported for triggers: `PhysicsSystem.cpp:828` guards on `!speculative`, and `:834` skips the solve for triggers, so a fast body crossing a thin trigger between steps fires no Enter and no Exit — checkpoints, kill planes and pickups missed by exactly the objects most likely to hit them.
- The sweep margin ignores rotation: `sweep = glm::abs(rigid->velocity) * deltaTime` (`:563`) feeds `pairMargin` (`:721`); `angularVelocity` is never consulted. `worldBounds` (`:153-162`) does give a conservative AABB, so the miss needs a thin obstacle against a fast tip — a swung bat, a propeller — not every rotating body.
- One collider per entity: `:593` and `:603` skip an entity that already has a shape, and `tests/test_physics.cpp:1656` enshrines it. The obvious workaround is worse than nothing — `SweepAndPrune` (`:257-287`) filters only on inverse mass, layer and AABB with no parent/child exclusion, so a child holding the second shape becomes a legitimate broadphase pair with its own parent and pushes it out of its own collider every step.
- Static surfaces have no material: `:882` falls back to file constants `kRestitution` (0.3) and `kFriction` (0.4) for anything without a `RigidBodyComponent`, and the colliders carry no material fields (`Components.hpp:455-505`). The workaround is cheap — kinematic bodies are skipped by the integrator (`:312`) and `:882` reads the material off any rigid body — but nothing in the docs or the inspector says so, so ice, mud and conveyors read as unauthorable.
- Queries use the AABB, not the shape the solver uses: `gatherShapes` (`:1131`) builds every query shape through `worldBounds` and collects a capsule as its bounding box (`:1156`), so a rotated crate is shot 41% too generously at 45° while the solver collides it exactly. The API is Raycast/OverlapSphere/IsGrounded and nothing else (`PhysicsSystem.hpp:79-99`) — no capsule sweep, so a move-and-slide character controller cannot be written, and `IsGrounded` is one downward ray, so a character half over a ledge reports airborne.
- Colliders are authored blind: the inspector edits size/center/radius/height at `InspectorPanel.cpp:435-478` and nothing draws them — grep for debugdraw/DrawCollider/wireframe across `src/` returns nothing. The most common physics-authoring mistake is the one the engine gives the least help with.

**Scripting / runtime**

- Scripts, animation and particles run off the fixed step: `ScriptEngine::Update` (`SupersonicApp.cpp:854`), `AnimationSystem::Advance` (`:860`) and `ParticleSystem::Update` (`:861`) all sit outside the accumulator that feeds physics at `:826`, and the ABI has one entry point with no fixed-tick counterpart (`ScriptPluginApi.h:196`) — only C++ layers get `OnFixedUpdate` (`:836`). `scriptAddForce` (`ScriptEngine.cpp:363-364`) applies a dt-free impulse, so a thruster accelerates twice as hard at 120 Hz. The reproducibility story does not reach the layer games are written in, and nothing in the docs concedes it.
- A script cannot resolve an entity id to a position: `raycast` (`ScriptPluginApi.h:65-69`) and `contactAt` (`:165-167`) hand back ids, and the only things the ABI can do with a foreign id are destroy, get/setVelocity, addForce, animation play and the UI setters. No `getPosition(entity)`, no find-by-tag. "Enemy chases player", "turret aims at target", "door opens within 3m" cannot be written. (Raycast's outPoint does give one world position per frame, so "aim at what's in front of me" is writable.)
- Authored parameters are floats only: `float (*param)(void*, unsigned, const char*, float)` (`ScriptPluginApi.h:129`) over `vector<pair<string,float>>` (`Components.hpp:617`). `spawnPrefab` takes a path and no authored parameter can carry one, so "this spawner emits that prefab" needs a plugin rebuild.
- A script cannot name a component the ABI did not anticipate: `ScriptEngine.cpp:453-466` special-cases `script.scriptName == "LightFlickerScript"` by string and mutates `LightComponent` directly, with the comment saying why. Widening a block is an ABI bump (`ScriptPluginApi.h:244-259` pins the sizes). Dimming a light, tinting a material or retuning an AudioSource means a new engine build.
- A prefab describes exactly one entity: `PrefabSerializer.cpp:122-124` creates one entity and the codec deliberately never writes the parent link (`ComponentCodec.hpp:28-29`); `HierarchyComponent` holds only `parent` (`Components.hpp:121-123`) so descendants would need a registry scan that neither save nor instantiate does. Saving a character or vehicle ships only the root, with a success message.
- A placed prefab has no link back to its source: `InstantiatePrefab` (`:120-124`) emplaces nothing recording origin, and grep for prefabPath/PrefabInstance/override across Components.hpp and ComponentCodec.cpp returns nothing. Editing `Enemy.prefab` does not touch the fifty enemies already placed — no apply, no revert, no overrides.
- There is no game project separate from the engine: `main.cpp:66` constructs `SupersonicApp` and runs it, `SupersonicApp::PushLayer` — documented at `SupersonicApp.hpp:49` as "the seam a game lives in" — has zero callers in `src/` or `tests/`, and `CMakeLists.txt` has no `install()`/`export()` so `SupersonicCore` (`:186`) cannot be consumed from outside. Packaging copies the running editor binary (`GamePackager.cpp:51`). A game's C++ is added by editing the engine's own main.
- Packaging is quiet about failure and has one destination: `GamePackager.cpp:70-73` calls `ec.clear()` right after `copy_file` so a missing DLL is reported as success, the asset copy is a hardcoded eight-name allowlist (`:83-87`) with `copyTreeIfPresent` returning true for anything absent (`:20-22`), and the sole caller passes the literal `"dist/GameRelease"` (`EditorLayer.cpp:368`). *You already know this — `ARCHITECTURE.md:1349-1356` documents all three.*

**Editor and input**

- Input bindings cannot be persisted or reached: `Input.cpp:118-150` hardcodes the action set, `Input.cpp` has no ifstream/ofstream/Json, and grep for SaveBindings/LoadBindings/bindings.json across `src/`, `tests/` and `docs/` returns nothing. The mechanism itself is fine — `BindActionKey` and friends are public statics (`Input.cpp:82-116`) and runtime rebinding is tested (`tests/test_input.cpp:245`) — what is missing is persistence and any route to them from a plugin or a shipped game. - One entity at a time: selection is a single `entt::entity` (`SceneHierarchyPanel.hpp:62`), the context menu has no Duplicate/Copy/Paste (`:193-215`), the hotkey block binds no Ctrl+D/C/V/Delete (`EditorLayer.cpp:466-505`), and the hierarchy has no text filter (contrast the console's, `EditorLayer.cpp:818`). Thirty crates is thirty create-and-retype cycles.
- Focus-on-selection is written and never called: `EditorCamera.hpp:28-29` declares it with the comment naming the feature, the definition is at `EditorCamera.cpp:66`, and grep finds zero callers. One line from working.
- No gizmo snapping or space toggle: `ImGuizmo::Manipulate` (`InspectorPanel.cpp:949-955`) is called with `LOCAL` hardcoded and the snap argument omitted; `InspectorPanel.hpp:46` holds only `m_gizmoOperation`. Modular corridors and 90° walls are eyeballed.
- Audio cannot be non-positional: `AudioSystem::Update` (`:63`) iterates `view<TransformComponent, AudioSourceComponent>` and pans everything unconditionally against the listener (`:100-106`), with no 2D flag on the component (`Components.hpp:507-522`). Music swings between speakers as the camera turns; a source without a transform is never started and nothing logs why. (Distance fade at least has a workaround — `attenuationFor` returns 1.0 below `referenceDistance`.)
- Audio clips and `.material` files are outside hot reload: the per-frame sweep (`SupersonicApp.cpp:940-948`) registers only `MeshComponent::filePath` and the two texture paths. `AudioSourceComponent::soundFile` and `MaterialComponent::materialPath` are never watched, `AudioEngine::m_clips` (`AudioEngine.hpp:52`) has no invalidation entry point, and `MaterialLibrary` has no Invalidate/Reload/Clear at all. Both have drop targets.
- Content-browser thumbnails go stale: `ThumbnailCache`'s API is Get/IsImage/Count (`ThumbnailCache.hpp:33-44`) with no Invalidate, and the watcher callback never reaches it. Edit a texture and the viewport updates while the tile shows the old preview for the rest of the session. (The 64-entry budget is deliberate — see below.)

## 5. NOT PROMISED, BUT MISSING — ranked

1. **A scripting path for anyone who is not a C++ programmer.** `plugins/CMakeLists.txt:7` is the whole plugin story — one shared library from one .cpp — and `ScriptRegistry.hpp:19-22` maps a name to a raw C function pointer, so a script is native code by construction. Every behaviour, including one-liners, is an edit-compile-link against a POD-only ABI whose only authoring surface is a float list. This is the single biggest limit on *who* can build a game here.
2. **Texture maps for anything but albedo and normal, and no alpha cutout.** The per-material descriptor set is a two-binding loop (`VulkanPipeline.cpp:301`); `shader.frag:287-289` reads roughness, metallic and AO from a single push-constant vec4 and emissive from one more (`:437`). No rust, no wet patch, no worn edge, no glowing screen. And there is no `discard` in `shader.frag` (grep hits only `grid.frag:30/:33`) and no `alphaCutoff` on `MaterialComponent` (`Components.hpp:283-322`) or `MaterialAsset`, so foliage and chain-link must go through the sorted blend path — where they self-sort wrongly and, per the sky bug above, get erased outdoors. This is the biggest limit on how a game here can *look*.
3. **Collision geometry beyond boxes, spheres and capsules — and no way to make two bodies move as one.** `GenerateTerrainMesh` (`TerrainGenerator.hpp:11`) returns a MeshData and `SceneHierarchyPanel.cpp:276-278` spawns "Procedural Terrain" with no collider, so the engine's own terrain is scenery you fall through; imported glTF level geometry arrives non-solid. Grep for meshcollider/convexhull/heightfield returns nothing. Compounding it, there are no joints: the component list runs Box, Sphere, Capsule and stops (`Components.hpp:455`), and grep for joint/hinge/ragdoll/constraint finds only animation joints and the internal contact `Constraint` at `PhysicsSystem.cpp:623`. With neither compound shapes nor joints, contacts are the only way two bodies can influence each other — no door on a hinge, no ragdoll, no vehicle.
4. **Mouse capture and text input.** `glfwSetInputMode`, `GLFW_CURSOR` and `glfwSetCharCallback` appear nowhere in `src/` — `InputPolling.cpp:76-79` only calls `glfwGetCursorPos`, so the cursor is always `GLFW_CURSOR_NORMAL`. A mouse-look game cannot ship: the cursor stays visible, hits the screen edge and stops turning, and a click outside drops focus mid-fight. Nothing can accept typed text either — no name entry, no chat, no in-game console.
5. **An animation system beyond a two-clip cross-fade.** `AnimationSystem.cpp:362` guards a single `BlendPoses` of exactly two clips; `AnimatorComponent` (`Components.hpp:529-556`) holds one clipName plus one blendFrom, and `AnimationClip` (`Skeleton.hpp:75-79`) is name, duration, channels — no event or notify track. Of the missing pieces, root motion and event tracks bite hardest: foot-sliding is unavoidable, and a footstep sound, a hit frame or a weapon-swap moment cannot be authored into a clip. Layers and blend spaces a script writing `clipName` can approximate badly.
6. **A UI that can show a picture.** `UITextComponent` (`Components.hpp:672`), `UIPanelComponent` (`:693`) and `UIButtonComponent` (`:719`) are the entire widget set — no UIImage, no container, no z-order, no focus state. Every element anchors directly to the game rect (`UISystem.cpp:50/79/116`) so there is no parent to lay out or clip inside, and drawing uses `ImGui::GetFont()` (`:76`) — one font, the editor's. No logo, no crosshair, no item art, and a pad-only player cannot move focus between menu buttons.

## 6. PLATFORM

- **Windows** — real. CI Debug leg, all 34 suites.
- **Linux** — more real than the docs admit. `ci.yml:51` configures Release, builds and runs all 34 suites at `:108-109`, plus lavapipe validation, ASan+UBSan and an options-off configure — all Linux-only legs. A genuine ALSA backend with its own writer thread and the software mixer (`AudioEngine.cpp:186-300`), dlopen hot reload (`HotReloadEngine.cpp:21-52`), `/proc/self/exe` (`ExecutablePath.cpp`). `ARCHITECTURE.md:1620`'s "should build and run; not verified on hardware" understates it — it is verified on a software rasteriser, which is worth saying instead.
- **macOS** — the seams are all present: Mach-O `ExecutablePath.cpp:20-43`, `.dylib` in `SupersonicApp.cpp:58-64`, the MoltenVK portability bit already set at `VulkanContext.cpp:129,175`. Missing: a CoreAudio backend (the branch is the documented no-op at `AudioEngine.cpp:302-319`) and a CI runner — there is none in `ci.yml`. Cost: a CoreAudio writer feeding the existing `AudioMixer`, which is the exact shape ALSA already uses, plus a runner. Days, not weeks.
- **Android** — the blocker is windowing, not `#ifdef`s. GLFW is added unconditionally and turns X11 and Wayland ON for any UNIX-not-APPLE (`third_party/glfw-3.4/CMakeLists.txt:37-38`), and `build_android.sh:42-48` disables neither. `AndroidNativeApp.cpp` exists and is filtered in (`CMakeLists.txt:165-167`) but has no windowing path. To make it real: drop GLFW on this target and create the surface from `ANativeWindow`, an AAudio/OpenSL backend, an APK packaging step, and a decision about the plugin (dlopen works on Android, but the shadow-copy scheme needs a writable path).
- **iOS** — same windowing problem (`GLFW_BUILD_COCOA` is ON for APPLE, which iOS implies, at `:36`; `build_ios.sh:29-33` disables nothing), plus a design consequence worth stating up front: iOS forbids dlopen, so the hot-reloadable plugin — the documented way to write gameplay here — cannot exist on that platform at all. `ScriptRegistry.hpp:19-22` becomes the only route and scripts must be statically linked. To make it real: MoltenVK over a `CAMetalLayer` surface, UIKit lifecycle, CoreAudio, and a static-script build mode.

## Deliberately simple, and the docs say why — not gaps

Don't let an audit talk you into re-litigating these: the physics departures at `ARCHITECTURE.md` §7j (no swept CCD, no persistent broadphase, no warm starting, one-point correction, unsimulated kinematics, single-threaded solver); two frames in flight with one primary command buffer and one queue (`:1059-1063`); the 64-thumbnail VRAM budget (`ThumbnailCache.hpp:42-43`, and `Get()`'s own comment at `:33-35`); the XAudio2-mixes-internally / ALSA-needs-a-software-mixer split (`AudioMixer.hpp:12-23`); the mobile no-op audio backend (`:1477-1485`); WAV-only synchronous decode (`:1499-1516`); `UIInput::Update` discarding click count (`:1463-1466`); `ScriptComponent::state` not serialised (`Components.hpp:627-630`); `SkinnedMeshComponent` not persisted because it is derived (`ComponentCodec.cpp:345`); tests touching no Vulkan entry point (`tests/CMakeLists.txt:11`); and queries rebuilding the shape list with no acceleration structure (`:940-942`). One near-miss worth noting anyway: because a kinematic body imparts no impulse (`:979-985`), a crate cannot ride a moving platform — that is a fundamental building block currently recorded as one bullet in a departures list.
