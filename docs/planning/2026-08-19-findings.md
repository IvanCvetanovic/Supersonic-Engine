# Supersonic Engine — Consolidated Roadmap

## Where this actually stands

The engine is a genuinely competent rendering and simulation core: correct Cook-Torrance PBR with normal mapping, four cascades plus point-cube and spot shadows with per-light slot indices, MSAA, an HDR chain with exactly one sRGB encode, GPU skinning with the joint palette in an SSBO, a version-gated hot-reload ABI that works, and a pure-logic test suite that is assertive rather than decorative (997 `CHECK` invocations across 7,150 lines, with real failure-path coverage of truncated WAVs, garbage glTF and malformed scenes). The repo's distinguishing habit — writing down *why*, including its own past bugs, in the code — is real and unusually good.

That habit has started to drift in five measurable places, and README.md:29-31 stakes the whole project on it not drifting: ARCHITECTURE §5's colour-pipeline table now says the opposite of `bloom_composite.frag`; VulkanOffscreen.cpp:93-97 explains a UNORM choice for a target that is now `R16G16B16A16Sfloat`; VulkanRenderer.hpp:28-30 claims the renderer "knows nothing about the editor" directly above VulkanRenderer.cpp:8-9's `#include "editor/Theme.hpp"`; shader.vert:18 promises to match `UniformBufferObject` and no longer does; and TimeTravelDebugger.cpp:50-52 promises rewinding restores motion, which stopped being true when `angularVelocity` was added.

The single biggest structural weakness is not any of that: **there is no content layer around the core.** Assets are identified by raw relative path strings re-resolved every frame with no invalidation and no release; there is exactly one scene, named by a `constexpr` in EditorLayer.cpp:26; and the editor cannot point an entity at your own model or audio clip at any price. The import stack is fully built — GltfLoader.cpp is 719 lines and works — and completely unreachable from the UI. Everything downstream (multi-level games, packaging the right scene, prefab reuse, art hot reload, asset renaming) is throttled by that one missing layer. The second weakness is observability: 62% of engine source (37 of 66 `.cpp`, 9,134 of 14,814 lines) is in no test target, there is no CPU or GPU timing instrumentation anywhere, and CI cannot launch the binary at all.

## Correctness defects

> **Status note.** Implementation is under way on branch `engine-roadmap`. The item below
> was found *after* this audit, while rewriting ARCHITECTURE.md, and is not one of the 39.

**A light parented to anything is positioned from its local offset, not its world position.**
`gatherLights` (VulkanRenderer.cpp:515-527) does `try_get<TransformComponent>` and reads
`transform->position` directly. `TransformComponent` is local to the parent —
`WorldTransformComponent` is the resolved one, and ARCHITECTURE.md §3b names reading it as the
thing that "makes parenting work everywhere at once". Everything else downstream does: the scene
pass, both shadow passes, viewport picking and the gizmo. Lights are the sole exception, so a lamp
attached to a moving vehicle lights the position it has *within* the vehicle, which for any parent
away from the origin is the wrong place entirely — and it does not move when the parent does.
Read `WorldTransformComponent` and take the translation column, falling back to
`TransformComponent` only when there is no resolved transform. `TransformSystem` already runs twice
per frame before the renderer, so the data is present and current at the point of use.
*Effort: hours.*

**ARCHITECTURE §5's colour-pipeline invariant table is inverted, and one in-code comment agrees with it.**
ARCHITECTURE.md:155-164 states "exactly **one** sRGB encode… it happens in `shader.frag`" and tables the offscreen target as `R8G8B8A8Unorm`. shader.frag's tail writes `outColor = vec4(color, …)` under "Linear, unbounded, un-encoded… Both steps moved to bloom_composite.frag"; VulkanOffscreen.hpp:20 sets `kColorFormat = BloomPass::kHdrFormat` = `eR16G16B16A16Sfloat` (BloomPass.hpp:46). Worse than the doc: VulkanOffscreen.cpp:93-97 still explains the UNORM choice as "shader.frag already encodes to sRGB itself", four lines above `colorAttachment.format = kColorFormat`. A contributor "restoring" UNORM silently deletes every above-white highlight, leaving bloom nothing to threshold — no error, no validation message.
Rewrite §5 as the real chain (linear HDR → Sfloat MSAA → bloom → composite tone-maps and encodes into `kOutputFormat` → ImGui blit), keep the "exactly one encode" framing, and delete the stale comment at VulkanOffscreen.cpp:93-97. *Effort: hours.*

**`SUPERSONIC_SCRIPT_API_VERSION` is enforced by an integer compare, so a struct change without a bump is silent cross-DLL corruption in the normal workflow.**
ScriptPluginApi.h:13-15 states the rule; HotReloadEngine.cpp:204-213 compares only `pluginVersion != SUPERSONIC_SCRIPT_API_VERSION`. Nothing pins a single `sizeof` or `offsetof` on `SupersonicScriptContext` (:106-119) or its four function-pointer tables. The obvious objection — "engine and plugin build together" — does not hold: rebuilding *only* the plugin while the engine keeps running is the entire point of hot reload, so a struct edit without a bump gives matching version integers and mismatched layouts, with `float position[3]` copied both ways every frame per scripted entity.
Add `static_assert(sizeof(...) == N)` plus `offsetof` assertions for all five structs, guarded by `#if SUPERSONIC_SCRIPT_API_VERSION == 5`. The plugin rebuild then fails to compile, forcing the bump. While there, add `angularVelocity` to `EntityStateSnapshot` (TimeTravelDebugger.hpp:17 has `velocity` only) so the recorder's own promise becomes true again. *Effort: hours.*

**The scene UBO is declared four times by hand and two copies have already drifted.**
`UniformBufferObject` (VulkanPipeline.hpp:44-72) is restated in shader.frag:24-36, shader.vert:25-35 and grid.vert:15-25. shader.vert carries "Must match Engine::UniformBufferObject" at :18 and then omits `ambientGround`, omits `spotViewProj[2]`, and declares `Light` as three vec4 against `GpuLight`'s four — so its `lights[]` lands at std140 offset 464 with a 48-byte stride where C++ writes 608 with 64. It is inert only because shader.vert reads `ubo.view`/`ubo.proj` alone (its one `ubo.` reference is at line 81). Four more constants are duplicated as GLSL literals: `lights[8]`, `cascadeViewProj[4]`, `SPOT_SHADOW_CASTERS 2`, `POINT_SHADOW_CASTERS 2`.
Extract `assets/shaders/scene_ubo.glsl` and `#include` it from the three shaders — glslc supports this natively and both compiler paths already exist at CMakeLists.txt:297-301. That deletes the problem in an hour; a `spirv-cross --reflect` size assertion in CI then guards one pair rather than three. *Effort: hours (include) → day (with the reflection check).*

**A packaged game launched from anywhere but its own folder silently boots the repo's scene.**
GameRuntime::Load anchors the manifest to `ExecutableDirectory()` (GameRuntime.cpp:50-53), but `m_manifest.startupScene` goes to `SceneSerializer::Deserialize`'s plain `std::ifstream file(filepath)` (SceneSerializer.cpp:188), and every shader (VulkanRenderer.cpp:293-294, BloomPass.cpp:275) and texture resolves the same way. `grep current_path src/` returns nothing, so nothing reconciles the two anchors. Running `dist/GameRelease/Game.exe` from the repo root finds `game.manifest` correctly and then loads the *editor's* working copy of MainScene.scene — a wrong-contents game, not a clean failure. From a shortcut with a foreign "Start in", it dies at pipeline creation instead.
Three lines: `std::filesystem::current_path(ExecutableDirectory())` when `manifest.isGame`. The proper version — an `AssetRoot()` / `ResolveAssetPath()` chokepoint — comes for free with the AssetDatabase below. *Effort: hours.*

**Json.hpp recurses without a depth limit, and non-finite floats make a saved scene permanently unloadable.**
Json.hpp:147-223 is mutual recursion with no depth counter; at MSVC's 1 MB default reserve, ~1,800 levels — roughly 2 KB of `[` — kills the process *inside* `Json::Parse`, which is exactly what SceneSerializer.cpp:196-200's non-destructive design was written to survive. Sharper, because it needs no hostile file: `writeVec3` (ComponentCodec.cpp:11-13) emits `inf`/`nan` through `ostream <<`, and `parseNumber` (Json.hpp:271-287) rejects all three; `grep isfinite|isnan|isinf src/` returns zero hits. Theme.cpp:162/177 draws Position/Scale as `DragFloat(…, 0.0f, 0.0f, …)` — `v_min == v_max` means ImGui does not clamp typed input, so ctrl-click and type `1e40`. Serialize then reports "Saved 18 entities" and writes a file that can never be loaded, PlayMode::Stop cannot restore, and EditHistory::Undo pops the target and drops it (EditHistory.cpp:53-56).
Add a depth counter failing past ~64 (enforced *during* parse — `Value`'s destructor is recursive too), a finite guard on both the write and read sides, trailing-content rejection, `insert_or_assign` for last-key-wins, and surrogate pairing. Add `tests/test_json.cpp` plus a mutation loop over MainScene.scene. *Effort: day.*

**No device features are enabled at all, so every texture is sampled at mip 0 forever.**
VulkanDevice.cpp:210 is `vk::PhysicalDeviceFeatures deviceFeatures{}` passed verbatim to `createDevice`, and `grep getFeatures src/` returns nothing. Downstream: VulkanImage.cpp:42 `mipLevels = 1`, :132 `anisotropyEnable = VK_FALSE`, :133 `maxAnisotropy = 1.0f`. The engine pays for 4× MSAA (three extra images plus resolve bandwidth) and then discards the filtering that matters more — MSAA anti-aliases geometry edges, not texture minification, so a textured floor at a glancing angle shimmers violently and no amount of MSAA fixes it. The same blank struct also costs `depthClamp` (which is why ShadowCascades.cpp:125 fits cascade depth to the whole scene and forced the bias retune at VulkanRenderer.cpp:330-336), `fillModeNonSolid` (no wireframe), `multiDrawIndirect` and `textureCompressionBC`.
Query `getFeatures()` in `isDeviceSuitable`, enable what is present, then give `VulkanImage` a mip count, `eTransferSrc` usage and a `vkCmdBlitImage` chain guarded on `eSampledImageFilterLinear` — the same check ShadowMap.cpp:39 already does. *Effort: day.*

**An invisible, mandatory, frictionless floor at y = 0 sits above the engine's own terrain.**
`kGroundPlaneY = 0.0f` (PhysicsSystem.cpp:15) is applied unconditionally to every non-kinematic body at :372-373 with no opt-out anywhere in `RigidBodyComponent`. The shipped terrain spawns at y = −2.0 (SceneHierarchyPanel.cpp:240) with a surface spanning [−1.2, +1.2] locally — so the *entire* terrain sits at y ∈ [−3.2, −0.8], wholly beneath the floor, and it carries no collider at all, so crates land on nothing 0.8 to 3.2 units above the visible ground while `IsGrounded` (:804) agrees. The clamp reflects `velocity.y` only: no friction, no angular response, while a box collider one unit away gets full Coulomb friction at :578-616. The same scene behaves like two different physical worlds depending on which surface you land on.
Delete the special case: a `PhysicsSettings` in the registry context (the mechanism AudioSystem.cpp:36 already uses), persisted by SceneSerializer, defaulting off; scenes wanting a floor emit a static 1000×1×1000 box that goes through the real solver. Budget for rewriting nine existing tests written against the plane. *Effort: few-days.*

**No CCD — projectiles tunnel from 24 m/s — and the one test named for it exercises a path that structurally cannot tunnel.**
Narrowphase is discrete overlap only (PhysicsSystem.cpp:470-492); no swept test, no speculative margin, no time-of-impact. At `kFixedPhysicsStep = 1/60`, capture requires `v ≤ 120·(hA+hB)`, so a 0.1-radius projectile against a 0.2-thick wall passes clean through above 24 m/s — slower than a thrown baseball. `testFixedStepDoesNotTunnel` (tests/test_physics.cpp:388-404) creates *one* entity, so `PhysicsSystem::Update` returns at :463 before any narrowphase runs, and then asserts `position.y >= 0`, which the ground clamp guarantees at any speed. And `kMaxPhysicsStepsPerFrame = 5` plus the accumulator zeroing at SupersonicApp.cpp:508-510 means a 200 ms hitch *deletes* ~2 steps of motion, so the real number is worse.
Expand each dynamic proxy by `velocity * dt` in the collect lambda and allow negative penetration up to that margin — one branch per pair, no new pass, covers ~80%. Full conservative advancement routes through `PhysicsSystem::Raycast`, which is AABB-based (:754-755), **so it must land after the OBB work below or bodies stop at the wrong surface.** Replace the vacuous test with a real two-body one. *Effort: few-days.*

## Architectural debt

**Every mesh and texture upload drains the entire GPU, inside the frame loop.**
`VulkanBuffer::CopyBuffer` ends with `GetGraphicsQueue().waitIdle()` (VulkanBuffer.cpp:124); VulkanImage does the same at :209 and :255. A mesh upload issues two, a texture three. All of it runs from `RenderSystem::SyncResources`, which SupersonicApp.cpp:549 calls *every frame* between `ImGui::Render()` and `DrawFrame`. `vkQueueWaitIdle` retires all submitted work, so each upload also flushes both frames in flight; a scene with 30 textures costs 90 pipeline flushes on first load, with glTF parsing (MeshRegistry.cpp:106) and stb decode on the same thread.
An `UploadContext` owning a staging ring, one command buffer and one fence: batch every transfer requested during a frame, submit once, free staging on fence signal instead of `waitIdle`. Renderables mid-upload keep the existing placeholder for a frame or two. Move glTF/stb decode onto the job system. This is the concrete reason nothing can stream. *Effort: day.*

**The shadow chain re-walks the entire ECS up to 18 times per frame, and nothing can measure it.**
`DrawFrame` records 4 cascade passes (VulkanRenderer.cpp:803-830), 2 point slots × 6 faces (:842-887) and 2 spot slots (:892-929). Each calls `RenderSystem::RenderDepthOnly`, which iterates the full `view<WorldTransformComponent, RenderableComponent>()` and runs `Frustum::TransformAABB` plus `try_get<SkinnedMeshComponent>` per entity, every time (RenderSystem.cpp:89-134) — 18 traversals before the scene pass's 19th. `Frustum::FromMatrix` is recomputed per cube face inside the loop (:881).
Build one flat `ShadowCaster` array (mesh id, world AABB, model, skin base/count) from a single pass, then test that array in all 18 passes; hoist `FromMatrix` out of the face loop. Do **not** skip passes for unclaimed slots — VulkanRenderer.cpp:836-841 documents why every slot is visited — use a per-slot dirty flag instead. *Effort: day.*

**No version field in any on-disk format, and no migration hook to hang one on.**
`writeScene` emits `{"Scene": "MainScene", "Entities": [` (SceneSerializer.cpp:50) — a name, no version. Prefabs are a bare component object with no envelope (PrefabSerializer.cpp:36-38); materials (MaterialLibrary.cpp:24-37) and `game.manifest` (GameRuntime.cpp:39-47) the same. Forward compatibility rests on `ComponentCodec::Read`'s per-field defaults, which handles a *added* field well and nothing else: a renamed key silently reverts to default, a changed unit loads as a plausible wrong number, and a newer file loads with the new fields dropped and reports success. One migration is already handled by type-sniffing — "Older scenes wrote a bare `true` here" (ComponentCodec.cpp:435-438).
Emit `"Version": 1` first in each writer; absent means 0, greater than current refuses with a message (SceneSerializer already returns exactly that shape). Add `MigrateScene(Json::Value&, int)` and move the particle special case into it as entry one. Cost is near zero today and rises with every scene anyone authors. *Effort: hours.*

**The editor serialises the whole scene to text every idle frame just to notice nothing changed.**
`EditorLayer::handleUndoRedo` ends at `m_history.CommitIfChanged(registry)` (EditorLayer.cpp:762) behind only four guards, so on every settled frame `capture()` runs `SceneSerializer::SerializeToString` through an `ostringstream` plus a full-string compare plus an entity-view walk (EditHistory.cpp:7-17, :37). MainScene.scene is 9,887 bytes for 18 entities — 549 B/entity — so the projection to a few thousand entities is megabytes of float formatting at 60 Hz to answer "no". Alongside it: `PhysicsSystem::Raycast` (:741) and `OverlapSphere` (:773) each call `gatherShapes`, walking the whole world into a fresh vector, and ScriptEngine.cpp:81 routes script `isGrounded` straight there — M scripted entities is O(M·N) plus M allocations per frame.
Hash while writing and keep the text only when the hash moves; then an explicit dirty flag set from ImGui widget return values and the ImGuizmo release boundary EditorLayer.cpp:758 already detects. Do **not** wire it to EnTT `on_update` sinks — the codebase mutates through `registry.get<T>()` references, so those sinks would silently drop every inspector edit. Keep the snapshot model; EditHistory.hpp:16-21 states why command objects were rejected. Give the query path a reusable buffer. *Effort: hours.*

**ComponentCodec is a hand-mirrored table whose own comments record two data-loss bugs from exactly that.**
`Write` (ComponentCodec.cpp:52-273) and `Read` (275-467) restate 18 components field by field with nothing able to iterate them. The file documents the consequences: `SphereColliderComponent` was never written, so "a sphere collider therefore vanished on Play, on Stop, on undo and on save - silently" (:141-143); `ParticleEmitterComponent` was written as a bare `true`, so "every emitter setting the user had authored was reset by the next load, Play, Stop or undo" (:231-237). Adding a component means five coordinated edits (Components.hpp, both codec halves, InspectorPanel's draw path, InspectorPanel.cpp:576-637's Add popup) and the build succeeds if you miss any. Latently, `Read` is documented as layering onto an existing entity (ComponentCodec.hpp:34-35) but calls plain `emplace` in 17 of 18 branches — `ENTT_ASSERT` in debug, silent corruption in release.
Cheap slice first: one `constexpr std::array` of the JSON keys each block emits, plus a test asserting every key appears when `makeFullyLoadedEntity` is serialised, plus a CI count check against `grep 'struct .*Component' Components.hpp` minus the three named exclusions. Switch `Read` to `emplace_or_replace`. The declarative descriptor table is the larger version. *Effort: hours (guard) → few-days (table).*

**Assets are identified by raw path strings, re-resolved every frame, with no invalidation and no release.**
`MeshComponent::filePath` and the two texture paths (Components.hpp:232-259) are the only asset identity, and nothing on `RenderableComponent` records that they were resolved — so `SyncResources` (RenderSystem.cpp:36-68) re-asks for every renderable every frame and `MeshRegistry::Acquire` (:86-91) rebuilds and hashes a `"file:" + path` string each time. Caching failures is deliberate; having no way to *un*-cache one is not — MeshRegistry.hpp and TextureRegistry.hpp expose no `Invalidate`, `Reload` or `Release`, so fixing a mistyped path needs an editor restart, while `MaterialLibrary::Create` (MaterialLibrary.cpp:140-150) already does exactly that repair. Both registries only grow. And the same `.gltf` is parsed twice on first use — MeshRegistry.cpp:105 for geometry, AnimationLibrary.cpp:16 for the rig — each a full synchronous tinygltf parse inside the frame.
`core/AssetDatabase`: stable id → { path, kind, refcount, handle }; components store the id, resolution happens when a path is authored or a scene loads, `SyncResources` reads a cached handle behind a dirty bit. Give both registries `Invalidate(id)`/`Release(id)` driven from the last-write-time poll HotReloadEngine.cpp:84-110 already implements — that is texture and mesh hot reload nearly free. Two sub-slices are a day each and independently useful: the cached handle, and sharing one `GltfLoader::Scene`. *Effort: week+.*

**Rotated boxes collide as world AABBs, one contact point, one solver pass, no warm starting, no sleeping.**
`collideBoxBox` (PhysicsSystem.cpp:168-195) tests `(a.halfExtent + b.halfExtent) - abs(delta)` on world AABBs and snaps the normal to one of six world axes at :184-193. For a 10×1×1 ramp at 30°, the AABB half-height is 2.933 against a true mid-surface 0.577, so a ball rests ~2.4 units above the visible ramp with a contact normal of exactly (0,1,0) and never rolls — you cannot build a slope. The response loop at :470-617 runs once, emits a single point at the overlap centre (:180-182, with the comment already conceding "a box settling flat still rocks slightly"), carries no impulse between steps, and has no sleep state, so every body is rebuilt from scratch each step — two `glm::inverse(glm::mat3(parentWorld))` per body, two fresh vectors, `getModelMatrix()`'s three `glm::rotate` calls. No test stacks more than two bodies.
Order matters: SAT over 15 axes with Sutherland-Hodgman face clipping first (it produces the multi-point manifold everything else needs, and puts a real orientation on `Body` so the inertia tensor stops being derived from a changing AABB), then 8 solver iterations with accumulated normal/tangent impulses, then sleep timers. Note the AABB-inertia choice at :423-437 is documented and self-consistent with the current narrowphase — it changes only because the narrowphase does. *Effort: week+.*

**VulkanRenderer contradicts its own stated invariant and carries four separable responsibilities in 1,053 lines.**
VulkanRenderer.hpp:28-30 says the class "Deliberately knows nothing about the editor"; VulkanRenderer.cpp:8-9 includes `editor/Theme.hpp` and `editor/EditorFonts.hpp`, and `initImGui` calls both at :663-664. One class owns the swapchain pass, the entire ImGui bootstrap, light gathering and slot assignment, cascade fitting, 18 inline shadow passes, and submit/present — and findings above land inside `DrawFrame` five separate times. This is also what makes an editor-free runtime build expensive: SupersonicApp.cpp:126-127 points the *scene* pipeline at `m_editorLayer->GetOffscreen().GetRenderPass()`.
Three cuts in value order: a `UiBackend` the editor owns (which restores the header's claim and removes the `editor/` include); a `ShadowRenderer` taking `Record(cmd, casterList, cascades)` — ~250 lines out of `DrawFrame`, and where the caster-list refactor above naturally lands; a `FrameContext{cmd, frameIndex, sceneSet, frustum, stats}`. What remains is swapchain, sync and present. *Effort: few-days.*

**Two frames in flight buy little, and three bloom pipelines are rebuilt from disk on every frame of a viewport drag.**
The UBO and joint palette are duplicated per frame, but there is exactly one `VulkanOffscreen` colour/depth/resolve set, one cascade map, one point map, one spot map and one bloom chain. VulkanOffscreen.cpp:163 says so outright — "single colour/depth target is shared by MAX_FRAMES_IN_FLIGHT frames" — which is why the `VK_SUBPASS_EXTERNAL` dependencies at :160-191 must declare WAR and WAW barriers. Every one of those is a serialization point: frame N+1's clear waits on frame N's whole scene pass, post chain and ImGui sample. Separately, `ApplyPendingResize` (VulkanOffscreen.cpp:71-89) does `waitIdle()` → `cleanup()` → `createBloom()`, and `BloomPass::buildPipeline` passes a **null** pipeline cache (BloomPass.cpp:337) and re-reads four SPIR-V blobs off disk — while the renderer's own `PipelineCache` sits unused at VulkanRenderer.cpp:282-284.
The resize half is hours: hand the cache in, cache the blobs, and hoist pipeline creation out of `BloomPass` entirely since pipelines depend on the render pass, not the extent. The target-duplication half is few-days and ~25-30 MB, and is worth proving with the timestamp queries below before committing. *Effort: hours → few-days.*

## Missing capability

**The hours-scale editor verbs that are simply not drawn.**
`RenderableComponent::isVisible` and `castsShadow` (Components.hpp:270-271) are serialised (:267-270, :460-465) and honoured by RenderSystem (:94, :147, :189) — and have no UI at all; `grep isVisible src/editor/` returns only two `emplace` calls. `InspectorPanel` has no remove-component path anywhere (`grep 'remove<|erase<' src/editor/` returns nothing), so adding a Box Collider by mistake is permanent. `ImGuizmo::Manipulate` is called with five arguments and `ImGuizmo::LOCAL` hardcoded (InspectorPanel.cpp:663-669), so there is no snapping and no world-space mode — you cannot make two cubes flush or rotate a tilted glTF about world Y. `EditorCamera::FocusOn` exists at EditorCamera.cpp:66, is documented as "used by 'focus on selection'", and `grep -rn FocusOn src/ tests/` finds only its declaration and definition — while EditorCamera.cpp:32-43 is the entire movement model (right-drag WASD; no orbit, no pan, no scroll zoom), so framing is the *only* realistic way to reach a selected object.
Two checkboxes, a deferred `registry.remove<T>` button per header, the 7th `snap` argument plus a mode toggle, and F wired to `FocusOn` using the `localBoundsMin/Max` RenderSystem already maintains. *Effort: hours. Highest ratio in this report.*

**You cannot point an entity at your own art from inside the editor.**
InspectorPanel.cpp:122-140 is the entire Mesh UI: a 4-item combo over primitives, `mesh.filePath` only ever *cleared* (:133) and shown read-only (:137). Audio is `TextDisabled("Clip: %s")` (:288) with no widget at all. Textures are raw `InputText` with no browse and no validation. ContentBrowserPanel has no `BeginDragDropSource` anywhere and reacts only to `.material` single-click and `.prefab` double-click, so a `.gltf`/`.png`/`.wav` tile is inert. Meanwhile MeshRegistry.cpp:102/143 dispatches glTF and OBJ and SupersonicApp.cpp:315/372 wires models in by hardcoded C++ string. Compounding it, the Add Component popup (:576-637) offers no Mesh, Material or Renderable — so "Create Empty" produces an entity that can never be made to draw.
Drag sources on file tiles with extension-derived payloads; drop targets on the Mesh header, both texture fields, the audio clip line, and the viewport `ImGui::Image` (spawning at the ray/ground hit — `ScreenPointToRay` is already at EditorLayer.cpp:631); a picker popup behind each for keyboard use. No new engine code — only UI plumbing to systems that already work. *Effort: few-days.*

**Nothing owns "the current scene", so a shipped game is one level by construction and "package the current scene" is false.**
`kScenePath` (EditorLayer.cpp:26) is the only argument to Save, Open and both shortcuts (:326, :330, :442, :446); no type anywhere tracks which scene is open or whether it is dirty (`grep isDirty|unsaved src/` returns nothing). `.scene` files get an icon and no behaviour (ContentBrowserPanel.cpp:27). GamePackager.cpp:95 hardcodes the same literal regardless of what is loaded and copies `assets/` off disk rather than serialising the live registry — so README.md:94's "One-click standalone build of the current scene" ships whatever was last written to MainScene.scene, with a success toast. `ScriptPluginApi.h` exposes no scene call, so no game can transition levels.
`core/SceneManager` owning `{currentPath, dirty}` with `Open`/`SaveAs`/`New` and a deferred `RequestLoad` applied between frames; File menu and content-browser double-click routed through it; `GameManifest.startupScene` written from the actual open scene; one deferred `loadScene` on the ABI plus a `PersistentComponent` tag. Until it lands, correct README.md:94 to name the fixed path. *Effort: few-days.*

**Scripts can steer a transform but cannot own data, spawn anything, or touch physics.**
The ABI is richer than a transform — input, raycast/isGrounded, animation and UI blocks (ScriptPluginApi.h:37-102) — and still has no per-entity storage, no authored parameters (`ScriptComponent` is name + enabled + an internal clock, and ComponentCodec.cpp:223-228 writes only Name and Enabled), no create/destroy, no velocity or force, and no collision or trigger callback. PhysicsSystem fills a contact list, SupersonicApp.cpp:499-505 accumulates it, and EditorLayer.cpp:740 draws a *count* — grep finds no other reader, so a trigger volume physically cannot fire. The engine's own sample proves the gap: SampleScripts.cpp:87 is `ctx->position[1] -= 4.0f * ctx->deltaTime`, a script-authored gravity, and :78 is a jump implemented as a teleport — necessary because physics runs at SupersonicApp.cpp:501 and scripts overwrite the result at :513.
Widen the existing C ABI behind one version bump rather than embedding Lua (the reload story and POD boundary already work): engine-owned per-entity state keyed by entity so it survives an unload; a name/float parameter list on `ScriptComponent`, edited and serialised; a `SupersonicScriptWorld` with `spawnPrefab`/`destroy` queued to the frame boundary plus get/setVelocity and addForce; and a second entry point fed from the contact list, diffed for enter/stay/exit. *Effort: week+. Largest single gameplay unlock.*

**Alpha is authored everywhere and honoured nowhere, and each particle costs a draw call.**
The inspector exposes 4-component albedo tint on every material (InspectorPanel.cpp:165, :195) and `ParticleEmitterComponent::endColor` defaults to alpha zero (Components.hpp:445); shader.frag:428 dutifully writes `albedoTex.a * push.albedoColor.a`. Nothing consumes it: `VulkanPipelineOptions::blendEnable{false}` (VulkanPipeline.hpp:123) is never overridden by `sceneOptions` — only the grid does, at VulkanRenderer.cpp:300 — and bloom_composite.frag ends `outColor = vec4(color, 1.0)`. Meanwhile RenderSystem.cpp:260-270 issues a `pushConstants` + `drawIndexed` per particle; ten emitters at the default 100 max particles is 1,000 draw calls a frame to render opaque cubes that shrink instead of fading. Glass, water, foliage, smoke and every fade-out are off the table, and the editor lies about it.
A second pipeline from the same shaders (`blendEnable`, `depthWrite=false`, `cullMode=eNone`) sharing both set layouts and the push block; partition the draw list into opaque (sorted by material — the existing `boundMesh`/`boundMaterialSet` rebind-avoidance at RenderSystem.cpp:203/213 is currently inert because nothing sorts) and transparent (back-to-front); an authored `blendMode` on `MaterialComponent`; and one instanced draw for particles. *Effort: few-days.*

**IBL and a skybox — the split-sum machinery is already written and fed a two-colour gradient.**
shader.frag contains the complete IBL structure: `fresnelSchlickRoughness`, Karis's `EnvBRDFApprox`, the `kD_ambient` split and a reflection-vector specular lobe — all of which feed `hemisphere()`, a `mix(ambientGround, ambientColor, dir.y*0.5+0.5)`. A mirror-metal sphere reflects a vertical gradient, and there is nothing behind it to reflect: the viewport clear is a flat `0.00023` with no skybox pipeline anywhere. Everything else is blocked or out of scope — SSAO, DOF and fog need depth, which VulkanOffscreen.cpp:141 discards with `storeOp = eDontCare`; TAA needs motion vectors and history, neither of which exists.
An `Environment` owning an equirect-to-cubemap skybox, a 32² irradiance map and a mip-chained prefiltered specular map, bound at set 0 bindings 5/6/7 (bound once per pass, so zero per-draw cost). In the shader it is two texture fetches replacing two `hemisphere()` calls. Draw the sky as a fullscreen triangle at depth 1.0 reusing `fullscreen.vert` and the grid-pipeline pattern. Flip the depth `storeOp` in the same change to unblock SSAO and fog later. *Effort: few-days.*

**Selection is one entity: no multi-select, duplicate, copy/paste, search or batch delete.**
SceneHierarchyPanel.hpp:32 is a single `entt::entity m_selectedEntity` and :35 a single `m_pendingDelete`, so deleting two things takes two frames. `grep -riE 'duplicat|paste' src/editor/*.cpp` returns nothing, and the hotkey block (EditorLayer.cpp:440-476) handles only Ctrl+S/O/Z/Y and W/E/R. There is no filter widget and no `ImGuiListClipper` anywhere in src/. The material handshake (EditorLayer.cpp:515-525) assigns to exactly one entity. Blocking out a level means re-running the create menu and re-dragging the gizmo per prop. (Note the hierarchy's delete-a-parent behaviour is *not* a bug — TransformSystem.cpp:170-181 preserves each orphan's world matrix by design; what is missing is a "Delete Hierarchy" option.)
`std::vector<entt::entity> m_selection` with a `Primary()` accessor so the inspector and gizmo keep working, Ctrl/Shift-click in `drawEntityNode`'s click branch, a vector `m_pendingDelete`, an `ImGuiTextFilter` drawing a flat list when non-empty, and Ctrl+D implemented by round-tripping `ComponentCodec::Write`→`Read` (PrefabSerializer.cpp:37/75 is exactly that). *Effort: few-days.*

**Colliders stop at sphere and box, with no local offset and no layer filtering.**
`enum class Shape { Box, Sphere }` (PhysicsSystem.cpp:51) is the whole vocabulary; `BoxColliderComponent` is `{size, isTrigger}` and `SphereColliderComponent` is `{radius, isTrigger}` (Components.hpp:326-334). No offset means a collider is locked to the entity origin and cannot be positioned. No layers means everything collides with everything: a bullet cannot ignore its shooter, a camera boom cannot pass through the player, a trigger meant for the player notices every crate. No capsule means no character controller — a box catches on every step edge, a sphere rolls.
The cheap slice is a day and unlocks most of it: `glm::vec3 center` on both components applied in the collect lambda and `gatherShapes`, plus `layer`/`collidesWith` masks tested in `SweepAndPrune` right next to the existing two-statics skip at :282, with mask overloads on `Raycast` and `OverlapSphere`. Capsule is ~150 lines of closest-point tests plus its inspector/serializer/test integration. Convex hulls (GJK/EPA) and a static triangle-mesh BVH are each week+ on their own and only worth it once environments stop being box soup. *Effort: day (offsets + layers) → week+ (full).*

**Light count is hard-capped at 8, and which 8 you get is EnTT pool order.**
`gatherLights` walks `registry.view<LightComponent>()` and does `if (count >= kMaxLights) break;` (VulkanRenderer.cpp:515) — with 50 authored lights, 42 vanish with no warning, and adding an unrelated component to a light entity can reorder the pool and change the scene's lighting. shader.frag:329 then loops all `count` lights per fragment with no bounds test, and the falloff at :346 is the legacy `1/(1+0.09d+0.032d²)` constant table, independent of `range` — at d = range = 25 it evaluates to 0.043, not 0, so every point light ends in a visible hard-edged sphere where the `continue` at :344 cuts it off.
Clustered forward, not deferred: deferred would cost a 3-4 target G-buffer, break the 4× MSAA resolve path, and force a shader.frag rewrite. Clustered is purely additive — set 0 is bound once per pass, so add bindings for a light SSBO, a 16×9×24 froxel grid and an index list, grow the descriptor pool by 3 per frame, build the grid on the CPU in `gatherLights` (no compute pipeline exists today), and swap the shader loop for the fragment's cluster range. One collision to plan for, not noted elsewhere in this report: clustering reorders lights into per-froxel index lists, which destroys the meaning of index 0 that shader.frag:377's `i == 0` shadow gating depends on. Directional lights are not spatially bounded, so keep them in a small always-on list outside the froxel grid and cluster only point and spot. Nothing changes in set 1, the push block, the vertex format or the loop shape. Replace the attenuation constants with a windowed inverse-square while there — that half is an hour and gives `intensity` a physical meaning. *Effort: week+.*

**Animation stops at a single cross-fade pair.**
`AnimatorComponent`'s entire blend state is one outgoing clip and one timer (Components.hpp:377-380), triggered implicitly by `animator.clipName != animator.activeClip` (AnimationSystem.cpp:252); `EvaluatePoses` blends exactly two poses (:359-373) and `BlendPoses` (:141-160) takes one scalar weight with no per-joint mask and no additive variant. The script ABI offers only `play` and `isPlaying`. `grep` for root motion or IK across src/ returns nothing. So every character is driven by a script string-comparing clip names; there is no speed-parameter walk→run blend, no upper-body reload over a lower-body sprint, and character movement drifts from the animation depicting it.
Build up from `BlendPoses`, which is already the right primitive: an `AnimationGraph` asset with 1D/2D blend nodes and named float parameters, plus `setFloat` on the ABI, is the useful first slice; a state machine with authored transitions is the second. Per-joint masks, two-bone IK (~80 lines, analytic) and root motion are each a separate line item after that — the full list is closer to a month than a week. *Effort: week+ (first slice: few-days).*

**"Package Standalone Game" ships the editor binary with a plaintext flag.**
GamePackager.cpp:50 copies the *running executable*, :56-73 sweeps sibling DLLs, :82-86 copies eight asset trees verbatim. The shipped binary therefore contains ImGui, ImGuizmo, the dockspace, three embedded base85 fonts (EditorFonts.cpp:16-18), ThumbnailCache, EditHistory and GamePackager itself; the only thing separating game from editor is `root["Game"].AsBool(false)` (GameRuntime.cpp:31) in a plain-text file a player can edit. The window is hardcoded `Window(1280, 720, …)` (SupersonicApp.cpp:108) with no resolution, fullscreen or vsync setting, and `Input.hpp:89` exposes only `LoadDefaultBindings()` with no file load/save — so a shipped game cannot have an options menu. Nothing verifies the packaged folder launches.
In value order: the path fix above; a `BuildSettings` block in the manifest (title, scene, width, height, fullscreen, vsync) written by a Project Settings panel and read at SupersonicApp.cpp:108; a CI job that packages, runs the result headless and asserts a clean exit. The `SUPERSONIC_RUNTIME_ONLY` build is the expensive part and is gated on the `UiBackend` split above — SupersonicApp.cpp:126-127 currently points the scene pipeline at the editor's offscreen render pass. *Effort: week+.*

**Audio: whole files decoded synchronously on the game thread, no buses, no voice cap.**
`AudioEngine::LoadClip` → `AudioClip::LoadWav` reads the entire file into a vector and keeps it (AudioClip.cpp:25-47), reached from `AudioEngine::Play` on the game thread the first frame a source starts (AudioSystem.cpp:84) — a three-minute stereo 44.1 kHz track is 31.7 MB resident and blocks the loop mid-gameplay. Only PCM and IEEE float are accepted (:89-92), so a shipped game carries ~10× the audio bytes it needs. `AudioSourceComponent` (Components.hpp:336-353) has no bus, group or priority, and nothing bounds live voices — no master/music/SFX slider is possible. Pan is `dot(toSource, listenerRight)` alone (:106); `listenerForward` and `deltaTime` are explicitly discarded at :61 and :46 with "reserved for cone attenuation / doppler".
Order: move the initial `LoadClip` onto the job system with a not-ready state and add a streaming ring-buffer voice; then a bus gain table multiplied in `SetVoiceParameters` plus priority-based voice stealing; then front/back attenuation and doppler from the already-available forward vector and delta. A CoreAudio arm is real but low value while ARCHITECTURE.md:218 records macOS as unverified on hardware. *Effort: week+.*

## If you only do three things

1. **Drag-and-drop asset assignment in the inspector and content browser.** It is the wall on day one — mesh and audio cannot be assigned at any price, and "Create Empty" makes an entity that can never draw — and the entire import stack behind it already works, so this is UI plumbing, not engine work.
2. **Plot `io.DeltaTime * 1000.0f` and add the per-system `ScopedTimer` enum.** The one-line half makes hitches visible today; the rest turns every performance item above from a guess into a measurement, which matters most for one person who cannot hold the whole frame in their head.
3. **Put velocity, forces and collision/trigger callbacks on the script ABI.** The engine computes restitution, friction, per-body inertia and triggers, hands the contact list to a HUD counter, and throws it away — and the sample script hand-rolls gravity as a position delta because it has no other choice. The hard part, a reload-safe versioned POD boundary, is already built.

## Candidate workstreams

**A. Your content, your levels — the authoring pipeline.** ~3-4 weeks. Bundles drag-and-drop asset assignment, `SceneManager` with New/Open/Save As and runtime `loadScene`, the AssetDatabase with ids and `Invalidate`/`Release` (which delivers art hot reload nearly free), the `AssetRoot()` path anchor, and packaging the real scene instead of the literal. **B. Make a game with it — gameplay authority.** ~2-3 weeks. **C. Prove it and describe it — observability, CI gates, and true docs.** ~2-3 weeks. **D. Stop the plastic look — the renderer's next visual step.** ~2 weeks. **E. Physics you can build a level on.** ~3-4 weeks, strictly ordered. **F. Scale past the demo scene.** ~3-4 weeks, and **do C first** — every item here is currently unmeasured. ## What two real games said was missing

Added after the audit, by reading **Wolf Brigade** (Godot 4.7, 2D lane RTS, Android-primary) and
**HUSK** (Rust/Bevy, 3D deterministic RTS) and asking whether this engine could host them.
**Wolf Brigade: no. HUSK: partly — the simulation yes, the game no.**

None of the engine's best-known limitations blocks either game. Not the eight-light cap, not
box-box-as-AABB, not the missing CCD, not the missing navmesh. HUSK's own notes say a physics
engine "would fight determinism" and it brings its own flow-field pathfinding; Wolf Brigade
contains no collider anywhere and does its combat as one-dimensional arithmetic. What blocks them
is that Supersonic is an *application with an editor fused into it*, and neither game is a scene —
they are programs.

**There is nowhere for game code to run.** `entt::registry m_registry` is private
(SupersonicApp.hpp:67, `private:` at :37) and the frame body is a fixed sequence with no callback
and no system-registration point. HUSK's 22-system chained schedule and Wolf Brigade's nine
singletons have nowhere to live but inside `SupersonicApp.cpp`. The plan knows the adjacent facts —
that `VulkanRenderer` includes editor headers, that the scene pipeline points at the editor's
offscreen render pass — but frames all of it as *subtraction*, getting the editor out of a shipped
binary. Both games need *addition*: getting a game into the loop. Same coupling, opposite
direction, and only one direction was written down. *Effort: week+.*

**There is no game clock.** The only fixed step is physics-internal, and it clamps the frame delta
to 100 ms before accumulating and zeroes the remainder after five steps — so it discards simulated
time under load. That would not break bit-exactness, but every mission timer and production queue
would run in slow motion. A 20 Hz sim also needs `prev`/`cur` transforms and interpolation by
overstep fraction or it visibly stutters. The engine violates its own would-be determinism rules
today: `ScriptEngine.cpp:246` accumulates `elapsed` from variable frame deltas and drives
`std::sin` off it. *Effort: week+.*

**Nothing the GPU owns has a lifetime.** `MeshRegistry` and `TextureRegistry` are write-once — no
update, no free, no eviction, storage private, and a key hit returns the cached id. HUSK rewrites a
240×240 fog texture every frame: same key is a no-op, a fresh key leaks a `VkImage` per frame, and
every mission transition leaks its terrain mesh and minimap image permanently. *Effort: few-days.*

**Transparency is a mechanic, not a finish.** `blendEnable = true` appears exactly once in the
renderer, for the editor grid, and `shader.frag` computes an alpha the blend state discards. What
that costs is fog of war, the build-placement ghost and the construction state. The roadmap has
this item bundled into the visual workstream and sold as quality-per-week; it is not a quality item
at all. *Effort: few-days.*

**No emissive term.** `EMISSIVE` names a material on 29 of HUSK's 58 models and carries its entire
team-state visual language, driven above 1.0 to trip bloom. Nothing in `src/` or `assets/shaders/`
mentions it, while everything downstream — Sfloat target, threshold-1.0 bright pass, Reinhard
rolloff — already exists, and `PushConstantData` has 24 spare bytes of its guaranteed 128. One
vec4 and one add. *Effort: hours. Best ratio in this section.*

**No instancing.** One `pushConstants` plus one `drawIndexed` per visible entity with no material
sort, re-run per shadow cascade. Instancing keyed by mesh+material does not fit a
push-constant-per-draw layout — changing the layout is the actual work. *Effort: week+.*

**The serializer cannot be opened to a game's own components.** `ComponentCodec` names 18 engine
types. Wolf Brigade's mid-match save and HUSK's snapshot are made of components it will never name.
`PrefabSerializer::InstantiatePrefab` also re-opens and re-parses the file on every call, which is
unusable at RTS spawn rates. *Effort: few-days.*

**Wolf Brigade's own list, honestly labelled as probably not worth it.** Orthographic camera
(`getProjectionMatrix` hardcodes `glm::perspective`; the only `glm::ortho` in the tree is the shadow
projection), an unlit shading path, world-space text (`UITextComponent` is screen-anchored by
construction), UI layout containers, per-system z-order that puts every button through a modal
overlay, a discarded "did the UI take this click" result, and Android with touch. That is a second
renderer and a windowing rewrite, not a feature gap. *Effort: month+ each; recommend not, unless 2D
becomes a goal in its own right.*

### What this corrected in the plan above

- **"If you only do three things" was answering a different question.** Items one and three —
  drag-and-drop asset assignment, and velocity/forces/collision callbacks on the script ABI — are
  things *neither game would ever use*. Wolf Brigade authors nothing in an editor; HUSK builds
  worlds programmatically. That list was written for someone sitting in the editor, and both of
  these games are programs that never open it.
- **Workstream B is mis-named.** "Gameplay authority" is, item for item, *script-ABI* authority,
  which is character scripting. Neither game is entity-scale, and `addForce` on entities a
  deterministic sim owns is precisely the coupling that desyncs a fixed tick.
- **Workstream E buys these two games nothing** except its final item, deleting the unconditional
  ground plane — which is worth pulling out and shipping alone.
